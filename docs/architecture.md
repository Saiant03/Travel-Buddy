# Arhitectură propusă — Travel Buddy

Evaluare documentară pentru o aplicație privată cu două conturi, în limitele planurilor gratuite. Sursele au fost consultate la 23 octombrie 2026 (Europe/Bucharest); prețurile, limitele și termenii se reverifică înainte de activarea serviciilor. Aceasta este recomandarea coordonatorului pentru planificare, nu o tehnologie activată și nici o garanție de cost zero sau funcționare integrată.

## Recomandare

**Cloudflare Pages (frontend static/PWA) + Cloudflare Worker (API) + D1 (date relaționale) + Firebase Authentication Spark (identitate).** Firebase se limitează la autentificare. Worker-ul verifică tokenul Firebase, aplică accesul la fiecare resursă și ține secretele de furnizori. API-ul privat servește datele fără cache partajat. Pagina introductivă poate fi publică; datele, conturile și operațiile sunt accesibile doar după autentificare.

Tavily Free este candidatul pentru căutare web, Groq Free pentru generare și conversația Buddy, iar Geoapify pentru geocodare, hartă și rute. Serviciile sunt adaptere înlocuibile, cu limite locale și erori explicite. Când se epuizează cota unui furnizor, se dezactivează doar funcția acelui furnizor (de exemplu căutări noi, generare sau hartă/rutare); datele deja disponibile online rămân consultabile atât timp cât API-ul și D1 funcționează. Nu se face upgrade automat.

## Autentificare și autorizare

Firebase Authentication este furnizorul gestionat de identitate; **nu se construiește autentificare sau hashing de parole propriu**. Alegerea este login Firebase cu email/parolă, confirmare email și resetare prin Firebase. Cele două conturi se precreează administrativ înainte de utilizare; aplicația nu are interfață de înscriere, invitație sau asociere publică. Worker-ul acceptă numai lista explicită a celor două Firebase `uid`, astfel că niciun alt cont, chiar cu email verificat, nu obține acces. Nu se presupune că înscrierea poate fi dezactivată complet la endpointul Firebase Auth în Spark; configurarea disponibilă se verifică la probe. Firebase Spark include autentificare fără facturare în cotele publicate; telefon/SMS nu se folosește.

Clientul trimite ID token-ul Firebase la Worker prin HTTPS în `Authorization: Bearer`. Worker-ul verifică înainte de orice citire/scriere: format și `alg=RS256`, cheia publică Google potrivită pentru `kid`, semnătura, `exp`, `iat`, `auth_time`, `email_verified=true`, `aud` identic cu Firebase project ID, `iss=https://securetoken.google.com/<projectId>` și `sub` nevid. Cheile X.509 se preia(u) de la endpointul oficial și se cachează conform `Cache-Control max-age`; `kid` necunoscut cere o actualizare controlată o singură dată. Eșecul de verificare sau indisponibilitatea cheilor în lipsa unei chei cache valide închide accesul. Apoi Worker-ul verifică dacă `sub` este unul din cele două UID-uri aprobate, iar pentru vacanță verifică apartenența la acel trip. ID token-ul nu se acceptă ca simplă valoare decodată.

Nu folosim Firebase Admin SDK cu cheie de service account în Worker. Pentru durata sesiunii, clientul folosește SDK Firebase și transmite token actualizat; tokenurile sunt scurte și verificabile local cu chei publice. Revocarea imediată nu se presupune: dacă devine necesară, trebuie verificată prin mecanism online sau politică suplimentară și măsurată. Nu se păstrează bearer token în URL. CORS restrâns la originile aplicației, validare de schemă și rate limit per UID se aplică separat de autentificare.

**Risc critic de probat:** Cloudflare Free permite 10 ms CPU pentru o invocare HTTP. Documentația Cloudflare menționează că verificarea autentificării și parsarea payload-urilor pot consuma 10–20 ms pentru sarcini mai grele. Cache-ul cheilor evită rețea la fiecare token, iar Web Crypto/JWT library mică poate fi suficientă, dar nu există dovadă pentru acest Worker și payload real. Gate-ul P-09 anterior extinderii implementării este p95 CPU ≤7 ms pe minimum 100 cereri cold și 100 warm, cu zero terminări CPU, pentru verificare JWT + allowlist/autorizare + parsare JSON până la 256 KiB + query D1. Pragul de 7 ms lasă headroom față de plafonul tare de 10 ms; se raportează p50/p95 și workload-ul. Orice p95 peste 7 ms sau terminare CPU înseamnă FAIL și cere revizuirea arhitecturii, fără upgrade implicit.

## Date, confidențialitate și sincronizare

D1 păstrează tabelele de utilizatori aprobați, profiluri, preferințe, ajustări per vacanță, vacanțe, baze/cazări, itinerarii/opriri, surse și propuneri Buddy. Constrângerile FK, unique și indecșii trebuie să exprime ownership/membership; fiecare query include `trip_id` și verificarea apartenenței în server, nu se bazează pe ID-uri greu de ghicit. Preferințele personale sunt editabile doar de proprietar. Vacanța și itinerariul sunt comune celor doi participanți. Păstrarea alergiilor/intoleranțelor cere câmpuri distincte de gusturi/refuzuri și reguli aprobate; nu deducem una din alta.

D1 Free publică 5 milioane rânduri citite/zi, 100.000 scrise/zi, maximum 500 MB pentru fiecare bază și 5 GB total pentru cont (limită per bază atinge prima). După limitele zilnice, interogările gratuite eșuează până la resetare UTC; nu există extindere fără plan plătit. Pentru două persoane volumul pare potrivit ca ipoteză, însă nu e măsurat. Worker static pages nu trebuie cache-uiască răspunsuri private: `Cache-Control: private, no-store` pentru API-ul personal, fără cache API/CDN pentru răspunsuri cu date; cache separat doar pentru asseturi publice nemodificabile. Nu include date sensibile, UID-uri sau prompturi în analytics/logs.

D1 este sursa comună. Clientul citește după login și trimite modificări cu `expectedVersion`; scrierile de plan cresc o versiune monotonă. Revalidarea are loc la focus și prin polling bounded la fiecare 15 secunde cât ecranul relevant este vizibil. La conflict, răspunsul poartă versiunea curentă, iar draftul/cererea locală se păstrează pentru adaptare și reconfirmare.

D1 `batch()` este o secvență tranzacțională de statementuri, nu o tranzacție interactivă cu branching JavaScript între ele. Propunerea Buddy păstrează `proposal_id`, `trip_id`, `base_version`, un snapshot/fingerprint al versiunilor preferințelor folosite, patch-ul și hash-ul conținutului. Conținutul propunerii este insert-only/imutabil; numai lifecycle-ul este derivat din receipt-ul de aplicare (fără receipt = pending, receipt = applied), fără câmp `state` scris separat. Clientul confirmă doar `proposal_id`, `expectedVersion` și `idempotencyKey`; patch-ul se citește exclusiv din propunerea salvată pe server.

Aplicarea începe cu lookup de receipt după cheia `(trip_id, uid, idempotency_key)`. Dacă există, se returnează rezultatul existent înaintea oricărei comparații de versiune; un retry identic nu trebuie raportat fals drept conflict. Dacă cheia încă nu are receipt, dar există receipt pentru același `proposal_id`, propunerea este deja aplicată și se returnează starea/receipt-ul existent, fără reaplicare, chiar dacă apelul a venit cu altă cheie. Dacă nu există receipt și starea/versiunea nu mai corespund, se întoarce conflict.

CAS-ul aplicării folosește un nonce unic `applyNonce` pe cerere și un singur `UPDATE ... WHERE` condițional al documentului planului. `proposal_id` are un singur receipt posibil, deci nu poate fi aplicat încă o dată cu o cheie diferită; cheile sunt scoped de trip și UID. Predicatul include `trip_id`, `version=expectedVersion`, apartenența UID-ului și `EXISTS` pentru propunerea exactă (`proposal_id`, `trip_id`, fără receipt de aplicare (deci pending), `base_version=expectedVersion`) plus versiunile/fingerprint-urile preferințelor relevante încă identice cu cele folosite la propunere. Astfel o propunere veche nu poate fi retrimisă de client cu o versiune nouă. Dacă preferințele relevante s-au schimbat, propunerea se invalidează sau se recalculează pe server și cere rezumat/reconfirmare nouă. `UPDATE` aplică patch-ul immutable citit pe server, incrementează versiunea și setează `last_mutation_nonce=applyNonce`.

În același `D1 batch()`, `INSERT ... SELECT` scrie receipt-ul cu `status=applied`, cheia idempotentă, UID, trip, proposal, versiunea nouă și `applyNonce`, numai dacă planul are exact versiunea nouă/nonce-ul și propunerea exactă nu are încă receipt (deci este pending) și are `base_version=expectedVersion`; constrângeri unice sunt `UNIQUE(proposal_id)`, `UNIQUE(trip_id, uid, idempotency_key)`. Receipt-ul este starea aplicată; nu se face un update separat necondiționat al propunerii. Pentru aceeași cheie sau același proposal concurent, o încălcare de unicitate anulează batch-ul care pierde competiția; handlerul face lookup după proposal/cheie și întoarce receipt-ul existent dacă există. Dacă receipt-ul lipsește și CAS-ul a afectat 0 rânduri, răspunsul este conflict; nu se raportează succes fără receipt. CAS cu `meta.changes=0` nu creează receipt și nu se raportează ca aplicat. Statementurile sunt atomice ca batch; orice eroare SQL unică anulează întregul batch. Dacă două apeluri cu aceeași cheie ajung simultan, al doilea verifică receipt-ul după eroarea de constrângere unică și returnează receipt-ul câștigător; același lucru se aplică două chei concurente pentru aceeași propunere. După un eventual collision server-side, lookup-ul de receipt precedă răspunsul de conflict. Această formă nu presupune tranzacții interactive și trebuie probată pe D1 API real.

Joburile de căutare/generare folosesc stare (`queued`, `running`, `complete`, `partial`, `failed`, `quota_exhausted`), progress real și `attempt_id`. Nu există promisiune că un job continuă în fundal singur: clientul apelează step endpoint limitat pentru fiecare pas. Endpointul face claim/lease cu `attempt_id`, un `claimVersion` monoton și un `leaseToken` unic per claim. El execută o singură unitate limitată; toate checkpoint/result/status writes au CAS pe job + attempt + claimVersion + leaseToken + starea așteptată, astfel încât un holder vechi să nu poată salva după revendicarea lease-ului. La abandon, lease-ul expiră; la revenire/retry manuală clientul poate revendica și relua din checkpoint. Timeout-ul nu anulează neapărat cererea la furnizor: un apel extern duplicat este posibil; se deduplică efectele locale, nu se promite deduplicare externă. Cota se rezervă conservator per tentativă înainte de apel; consumul necunoscut după timeout nu se rambursează automat, ci se reconciliază când furnizorul expune utilizarea. Pollingul este bounded (la fiecare 15 secunde doar cât e vizibil) și mai rulează la focus.

## Fotografii și obiecte

Nu se folosește stocare obiectelor cu billing/subscription în arhitectura zero-cost (inclusiv R2: înrolarea cere activarea unui abonament, iar allowance-ul gratuit nu este un hard cap care să garanteze imposibilitatea taxării). Firebase Cloud Storage cere Blaze din 3 februarie 2026 și este exclus la fel. Ilustrațiile/cardurile editoriale proprii stau ca asseturi statice în Pages. Fotografiile locurilor sunt URL-uri licențiate de la furnizori/surse care permit afișarea și, separat, cache-ul local pentru uz offline; se salvează licența/atribuirea, URL-ul, sursa și data verificării. Nu se presupune că rezultatul găsit poate fi hotlink-uit, proxy-uit sau copiat. Respectăm termenii și drepturile sursei; când hotlink/cache nu este permis, nu afișăm fotografia, folosim asset editorial cu etichetă clară sau marcăm fotografia indisponibilă.

Când termenii sursei permit proxying, browserul cere imaginea prin endpoint autentificat al Worker-ului. Endpointul acceptă numai URL-uri deja legate de un loc în D1 și hosts/paths preautorizate, verifică apartenența la trip, HTTPS, redirecturi și MIME image allowlist; blochează adrese private/loopback, redirecturi către alte hosturi, SVG/HTML și content-type fals. Răspunsul are plafon de dimensiune (de ex. 2 MiB) și timeout scurt, streaming într-un byte limit, rate limit per UID/zi, `Cache-Control: private, no-store` și CORS doar originul aplicației (sau omiterea CORS dacă endpointul este same-origin); fără `*`, cu `Vary: Origin` dacă se reflectă originul validat. Redirecturile sunt dezactivate sau validate la fiecare hop; niciun URL arbitrar furnizat de utilizator nu devine proxy deschis. Worker Free are 50 external subrequests per invocation și 100.000 request-uri/zi; o cerere de imagine consumă subrequest extern, deci fluxul trebuie să folosească o imagine per request și să refuze cererile peste limită.

Fiecare snapshot este cheiat separat prin `(ownerUid, tripId, locale)` și păstrează `sessionGeneration`; pointerul activ este și el scoped după aceste chei. Citirea și commitul validează că owner-ul și locale corespund sesiunii locale curente și snapshotului cerut. Înainte de salvare, serverul fixează manifestul fotografiilor eligibile pentru snapshot; orice fotografie fără drept de cache este tratată upstream ca „indisponibilă” și reprezentată astfel în manifest înainte să înceapă download-ul. Orice fotografie declarată eligibilă în manifest trebuie descărcată prin proxy și salvată ca Blob în namespace-ul temporar IndexedDB. Dacă una eșuează sau depășește limita, noul snapshot nu se declară complet și pointerul rămâne pe copia veche; nu se omite silențios fotografia cerută. Un placeholder de „fotografie indisponibilă” poate intra în manifest doar dacă sursa/permisiunea a fost clasificată astfel înainte de salvare și manifestul îl declară explicit. Service Worker și cache HTTP comun nu păstrează răspunsuri private; online se revalidează sau se cere din nou.

## Copie offline atomică

Frontend-ul este PWA: service worker cache-uiește doar shell-ul public și asseturile editoriale versionate; nu cache-uiește răspunsuri private. IndexedDB păstrează snapshotul personal și blobs/miniaturi de fotografie permise. La salvare manuală descarcă și validează un snapshot complet cu `snapshotVersion`, limbă și lista resurselor, apoi scrie într-un namespace temporar. După ce toate răspunsurile și imaginile permise sunt stocate cu succes, o tranzacție IndexedDB comută indicatorul `activeSnapshotId` către noua copie. Copia veche se șterge numai după confirmarea commitului; eșecul lasă vechea copie activă și afișează starea reală. La pornire offline se citește numai snapshotul indicat de pointer. IndexedDB tranzacțiile sunt atomice în sfera lor, dar browserul poate evacua stocarea sau utilizatorul o poate șterge; afișăm data ultimei copii, gestionăm lipsa datelor și oferim export/backup doar dacă produsul aprobă separat.

Cache-ul comun nu conține API responses sau fotografii personale. Offline-ul este permis numai pentru snapshotul complet salvat pe dispozitivul respectiv; o sesiune expirată în timp ce dispozitivul este offline permite doar acel snapshot deja salvat până la logout, fără sync ori API online. La începutul logout-ului clientul invalidează/incrementează `sessionGeneration` și blochează imediat citirea tuturor snapshoturilor; apoi șterge snapshoturile, blobs IndexedDB, datele de sesiune și orice private cache local. Citirea sau commitul după logout/account switch nu poate rezolva pointerul altei sesiuni ori al altui `ownerUid`; dacă purge-ul se întrerupe, markerul logout rămâne și snapshoturile nu se deschid până la curățarea/reautentificarea corectă. Logout local nu revocă automat Firebase ID token-ul deja emis: dacă tokenul a fost copiat, el poate rămâne valid până la expirare cât timp UID-ul este allowlisted. Clientul șterge credentialul local la logout, iar API-ul continuă să verifice tokenul/UID-ul; nu se pretinde revocare imediată. În timp ce offline, sesiunea expirată permite doar snapshotul existent până la logout, fără sync/API online; revocarea efectivă prin eliminarea UID-ului allowlisted este administrativă și separată.

## Frontend și API modular

Recomand frontend TypeScript cu Vite/React, HTML static pe Cloudflare Pages și manifest PWA/service worker. Contractele sunt planificate ca tipuri/interfețe fără implementare în acest document:

- `AuthPort`: obține/refresh token managed, sign-in/out, stare email verificat.
- `IdentityVerifier`: input bearer token; output `VerifiedPrincipal { uid, emailVerified }` sau eroare; adaptat Firebase ID JWT.
- `AccessPolicy`: validează UID allowlist, ownership de profil și apartenența la vacanță.
- `TripRepository`, `PreferenceRepository`, `ProposalRepository`, `JobRepository`: API-uri persistente, fiecare cu versiune și rezultat tipizat.
- `TripService`: reguli de produs pentru vacanță, proprietari și membri.
- `BuddyProposalService`: construiește propunere și rezumat diferențelor; aplicare prin compare-and-swap plus idempotency.
- `SearchProvider` / `TavilySearchAdapter`: query, rezultate cu sursă/timestamp și consum de cote.
- `LanguageModelProvider` / `GroqAdapter` și alternativă `WorkersAIAdapter`: input minimal și output JSON validat; reguli aprobate aplicate în cod.
- `GeocodingProvider`, `RoutingProvider`, `MapTileProvider` / `GeoapifyAdapter`: coordonate, geometrie, atribuire și stare de acoperire.
- `ImageProvider` / `LicensedImageSource` și `AuthenticatedImageProxy`: verificarea dreptului/hostului, fetch limitat și livrare fără cache partajat.
- `OfflineSnapshotStore`: validate, prepare, commit pointer, load, remove.

Valoarea provider-ului se selectează prin configurare privată server-side; cheia nu intră în bundle client, URL, log sau răspuns. Toate răspunsurile AI se validează prin schemă și reguli de domeniu. Refuz explicit al oricăruia exclude activitatea comună, alergiile și intoleranțele nu sunt gusturi, iar regulile alimentare aprobate sunt bariere deterministe. Payload-ul către Tavily/Groq exclude nume și email; transmite numai destinația/perioada, preferințele strict necesare și rezultatele/sursele necesare. Datele despre alergii sunt sensibile și intră în prompt doar dacă sunt necesare și explicit permise în produs; altfel filtrarea se face local/server-side și modelul primește doar condiția minimală rezultată.

## Furnizori auxiliare și limite

- **Tavily Free:** 1.000 API credits/lună, fără card conform paginii curente; resetare lunară în ziua 1 și apelurile se opresc la epuizare. Nu înseamnă 1.000 vacanțe; search/extract/crawl consumă diferit.
- **Groq Free:** exemplul curent `openai/gpt-oss-120b`: 30 cereri/minut, 1.000/zi, 8.000 text tokens/minut, 200.000/zi; limitele diferă de cont/model și răspund cu 429 la depășire. Măsurăm calitatea RO/EN/FR și tokenii per generare. Nu există promisiune de calitate sau disponibilitate.
- **Workers AI:** alternativă Cloudflare, cotă gratuită publicată de 10.000 neurons/zi; costul depinde de model și mărimea inputului/outputului, iar documentația actuală marchează unele modele ca disponibile numai pe plan Workers Paid. Se verifică modelul concret și planul înainte să fie considerată fallback efectiv gratuită.
- **Geoapify Free:** 3.000 credite/zi în oferta curentă, pentru apeluri combinând geocodare, locuri, tile-uri și rute; include cerințe de atribuire și limite de folosire. Acoperirea și precizia transportului public variază; când datele sunt modelate/aproximative interfața marchează acest fapt. Nu afișăm distanțe/durate dacă brief-ul nu le cere.

Cotele furnizorilor externi și limitele Cloudflare/D1 sunt separate și pot fi schimbate. La epuizarea Tavily/Groq/Geoapify se oprește ori se marchează indisponibilă numai funcția afectată, iar restul datelor existente se citesc online cât timp infrastructura proprie este disponibilă. La limita zilnică Worker sau D1, la eroare ori indisponibilitate a infrastructurii, API-ul poate să nu poată servi nici datele deja sincronizate în cloud. Interfața explică faptul că nu se poate conecta și oferă deschiderea copiei locale complete salvate anterior sau reîncercarea; fără copie locală, datele cloud nu sunt garantat accesibile în acel moment. Rămân accesibile shell-ul public cache-uit și copia locală disponibilă pe dispozitiv. Nu promitem disponibilitate 100% pentru un serviciu gratuit. Aplicația afișează epuizarea/indisponibilitatea și nu pornește apeluri suplimentare automat ori upgrade cu plată.
